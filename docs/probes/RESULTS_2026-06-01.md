## Verdict

**Mixed** — All 6 commands prompted, including Test 1 (a bare, single allowed command). This is broader than the doc's "Tests 3, 5, 6 PROMPT → keep hook" branch:

- The 5/30 per-segment hypothesis is **refuted**: chains of allowed commands (T3, T5, T6) prompted.
- But Test 1 also prompted, even though it's a bare `touch /tmp/probe_sanity` with `Bash(touch *)` explicitly in the project allow list. So we cannot conclude the matcher has merely "flipped back to whole-string" — something more fundamental is going on. Either (a) the matcher is broken or has changed semantics so even single-command rules don't match, or (b) `--setting-sources project` is not loading this directory's `settings.json` at all (e.g., it may look for `.claude/settings.json` at a project root, not a bare `settings.json` in CWD).

Recommendation for the parent session: keep the chain-blocking hook (it's not over-blocking — chains *are* prompting). Before writing a FINDINGS entry, isolate (a) vs (b) — e.g., re-run with verbose/debug logging to confirm which settings file Claude Code is actually loading, or place a `.claude/settings.json` at the dotfiles repo root with the same allow rules and re-run.

## Post-run diagnosis (added after verdict)

The "Mixed" verdict above is **wrong** — or rather, it described the symptoms accurately but misdiagnosed the cause. After the 6 tests, we investigated why bare T1 (`touch /tmp/probe_sanity`) prompted despite `Bash(touch *)` being in `settings.json`, and found:

- `claude --help` documents `--setting-sources` as accepting `user, project, local`.
- The `project` source loads `.claude/settings.json` at the project root — **not** a bare `settings.json` in CWD.
- The probe's `settings.json` was placed at `probes/settings.json` (bare file in a subdirectory), so `--setting-sources project` never loaded it. The session ran with **zero allow rules**, which is why every command prompted — including `ls`, `claude --version`, and bare T1.
- Confirming side-evidence: `/Users/dan/code/dotfiles/.claude/` contains only `agents/` and `settings.local.json` — no `settings.json`. So neither the probes/ file nor a dotfiles-root file was being loaded as `project`.

**Implications for the 2026-05-30 finding:** Not refuted. We never actually re-probed the matcher; we ran a no-rules-loaded session and watched everything prompt. The matcher's actual chain behavior remains unknown for 2026-06-01.

**Fix staged**: `probes/settings.json` moved → `probes/.claude/settings.json`. A new session launched from `/Users/dan/code/dotfiles/docs/active/chain-hook-maintenance/probes/` with `--setting-sources project` should now load the rules. Caveat: if `--setting-sources project` actually searches for `.claude/settings.json` at the *git project root* (`/Users/dan/code/dotfiles/.claude/settings.json`) rather than CWD, the move won't help and we'd need `--settings <file>` instead. The next probe will reveal which.
